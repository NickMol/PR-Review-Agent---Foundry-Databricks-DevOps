Step-by-step setup guide

Phase 1 — Databricks workspace (~2 min)

Goal: get a PAT token to authenticate from Azure DevOps.

1. Open your Databricks workspace
2. Top-right corner → click your profile icon → Settings
3. Left menu → Developer → Access tokens
4. Click Generate new token
  - Comment: azure-devops-poc
  - Lifetime: leave default (or set 90 days for PoC)
5. Copy the token immediately — you won't see it again.
   Store it ONLY in the Azure DevOps variable group (Phase 3). Never paste it into a file.

⚠️  If you already generated a token and saved it here, revoke it in Databricks immediately
    (Settings → Developer → Access tokens → Revoke) and generate a fresh one.

---
Phase 2 — Azure DevOps: create repo and push code (~10 min)

Goal: get your local code into Azure DevOps.

1. Go to your Azure DevOps organization → New project (or use an existing one)
2. Inside the project → Repos → New repository
  - Name: medallion-poc
  - No README, no .gitignore (you already have the code)
3. Azure DevOps shows you the remote URL and init commands. In your terminal, run from the Databricks Poc okt folder:
cd "C:\Users\nick.mol\OneDrive - Accenture\Desktop\Databricks Poc okt"
git init
git add .
git commit -m "Initial commit — medallion PoC"
git remote add origin <url-from-azure-devops>
git push -u origin master
4. Create the two other long-lived branches from master:
git checkout -b dev
git push -u origin dev
git checkout -b uat
git push -u origin uat
5. Back in Azure DevOps → Repos → Branches → set dev as the default branch
   (three-dot menu next to the branch → Set as default).
   This is the branch developers clone and branch off from.

---
Phase 3 — Azure DevOps: variable group (~3 min)

Goal: store the Databricks credentials so the pipeline can use them without hardcoding.

1. Left menu → Pipelines → Library
2. Click + Variable group
3. Name: databricks-medallion
4. Add two variables:

| Name             | Value                                        | Secret?                   |
|------------------|----------------------------------------------|---------------------------|
| DATABRICKS_HOST  | https://<your-workspace>.azuredatabricks.net | No                        |
| DATABRICKS_TOKEN | <the PAT you copied in Phase 1>              | Yes — click the lock icon |

5. Click Save

---
Phase 4 — Azure DevOps: create the pipeline (~3 min)

Goal: wire up azure-pipelines.yml so Azure DevOps knows to run it.

1. Left menu → Pipelines → Pipelines → New pipeline
2. Where is your code? → Azure Repos Git
3. Select your medallion-poc repository
4. Configure → Existing Azure Pipelines YAML file
5. Branch: master, Path: /medallion-poc/azure-pipelines.yml
6. Click Continue → Save (not Run yet — environments don't exist yet)

---
Phase 5 — Azure DevOps: create environments with approval gates (~5 min)

Goal: make UAT and PRD deployments pause for a human sign-off before they run.

1. Left menu → Pipelines → Environments → New environment
  - Name: uat, Resource: None → Create
2. Open the uat environment → top-right three-dot menu → Approvals and checks
3. Click + → Approvals
  - Add yourself (or a group) as approver
  - Instructions: Validate results in dev before approving UAT deployment
  - Create
4. Repeat steps 1–3 for an environment named prd
  - Instructions: Sign-off after UAT validation before promoting to production

---
Phase 6 — Azure DevOps: branch protection policies (~5 min)

Goal: prevent anyone (including yourself) from pushing directly to dev, uat, or master — all changes must go through a PR.

Do this for each of the three branches: go to Repos → Branches, hover over the branch name, click the three-dot menu → Branch policies.

Minimum recommended settings:

┌───────────────────────────────────────┬────────────────────────────┬──────────┬──────────┐
│                Policy                 │            dev             │   uat    │  master  │
├───────────────────────────────────────┼────────────────────────────┼──────────┼──────────┤
│ Require a minimum number of reviewers │ 1                          │ 1        │ 1        │
├───────────────────────────────────────┼────────────────────────────┼──────────┼──────────┤
│ Check for linked work items           │ Optional                   │ Optional │ Optional │
├───────────────────────────────────────┼────────────────────────────┼──────────┼──────────┤
│ Build validation (run the pipeline)   │ Add — select your pipeline │ Add      │ Add      │
└───────────────────────────────────────┴────────────────────────────┴──────────┴──────────┘

For Build validation, this runs a validate-only check on PRs before they can be merged. The actual deploy only happens after merge.

▎ Note: with a single-person PoC you can set reviewers to 1 and approve your own PR, but having the policy in place proves the pattern.

---
Phase 7 — First end-to-end run

Once everything above is in place:

1. Make a small change on a feature/test-run branch (e.g. add a row to sample_orders.csv)
2. Push and open a PR → dev
3. Approve and merge
4. Watch Pipelines → the Deploy_Dev stage kicks off automatically
5. When it passes, open a PR from dev → uat
6. Merge → pipeline pauses → you get an approval notification → approve → Deploy_UAT runs
7. Same flow for uat → master → Deploy_PRD
